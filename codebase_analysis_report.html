01 Executive Summary

The NV Cyclothon web platform is a modern, high-performance event management and commercial sponsorship system built for the 3rd Edition of NV Cyclothon scheduled for 22 November 2026 in Rewa, Madhya Pradesh, organized by the Rewa District Cycling Association (RDCA).

The platform coordinates public outreach, multi-category participant registrations (60 KM Road, 30 KM MTB, 10 KM Green Ride, 2.5 KM Kid-o-Thon), Razorpay online payment integration, on-day QR code-based volunteer check-in, real-time community engagement walls, automated PDF pass and certificate generation, commercial partnership & vendor onboarding, and a centralized administrative workspace.

Core System Capabilities

  • Participant Registration Engine: 500+ expected riders, tiered registration fees, automated ticket payload generation, waiver enforcement, and duplicate phone/email prevention.
  • Financial Gateway Integration: Razorpay payment orders with cryptographically verified signatures (HMAC-SHA256) and webhook capture handling.
  • Volunteer Race-Day Check-in Subsystem: Low-latency QR-code scanner and manual search supporting instant check-in verification with audit trails.
  • Partners & Commercial Vendors Portal: Dedicated corporate sponsorship packages (Title Sponsor ₹5,00,000 down to Supporting Partners ₹50,000), 13 vendor categories, multi-step application forms with draft persistence, and deliverables tracking.
  • Document Generation Service: In-memory dynamic PDF rendering for official Rider Passes (with QR code and bib styling) and Participation Certificates using pdf-lib and pdfkit.
  • Dual Client Architecture: Clean separation of public visitor surface (index.html) and high-security administrative operations (internal.html).

02 High-Level Design (HLD)

The platform utilizes a decoupled client-server architecture with an Express.js REST API backend backing dual single-page application (SPA) builds generated by Vite. The backend employs an abstract repository pattern supporting both production PostgreSQL and an in-memory Mock database for unit testing.

Architectural Tenets

Architecture Pillar Design Decision Technical Rationale
Dual Entry Build Separated main.jsx and internal-main.jsx Ensures internal administration code and sensitive parsing logic are not bundled into public visitor bundles, decreasing initial bundle size and surface attack area.
Repository Pattern PostgresRepository and MockRepository with identical interfaces Allows unit tests (Vitest) to execute without requiring an external PostgreSQL instance, running 15 full E2E test suites in under 2 seconds.
Direct-to-Buffer Storage Multer memoryStorage with Sharp transcoding No temporary files touch disk before validation; images are re-encoded to WebP format, stripping malicious EXIF data and neutralizing polyglot attacks.
Stateless Dual Scoped Tokens Custom HMAC-SHA256 signed bearer tokens Separate token scopes (admin vs volunteer_checkin) with configurable TTLs (15 min admin, 8 hr volunteer) requiring no centralized session cache.

07 Security & Risk Audit

An exhaustive security analysis of the backend and frontend code revealed several key defensive strengths, alongside four critical-to-medium security findings that must be remediated prior to high-traffic public launch.

Summary of Security Posture
The application demonstrates excellent defensive coding practices in SQL parameterization, input schema validation (Zod), and image transcoding (Sharp). However, an access control bypass exists on legacy product endpoints, and token revocation is not supported.

Detailed Vulnerability Findings

1. Unauthenticated Product Modification & Deletion (Broken Access Control)

CRITICAL (CVSS 8.5)

File Affected: backend/src/app.js (lines 174–180) and backend/src/routes/products.js

Vulnerability Description: The products router is mounted at app.use("/api/products", createProductsRouter({ ... })) without any authentication middleware. Within products.js, the routes POST /, PATCH /:slug, and DELETE /:slug are defined without checking for an administrative token.

Exploit Scenario: Any anonymous attacker on the internet can craft a DELETE /api/products/saffron-gold or POST /api/products request to delete catalog items or insert arbitrary spam records into the database.

Remediation: Apply requireAdmin(config) to all mutating HTTP methods (POST, PATCH, PUT, DELETE) on the products router.

// In backend/src/routes/products.js:
const { requireAdmin } = require("../services/security");

router.post("/", requireAdmin(config), async (req, res) => { ... });
router.patch("/:slug", requireAdmin(config), async (req, res) => { ... });
router.delete("/:slug", requireAdmin(config), async (req, res) => { ... });

2. Non-Standard Token Implementation with No Revocation (Replay Window)

HIGH (CVSS 7.2)

File Affected: backend/src/services/security.js

Vulnerability Description: The system implements a custom token signing algorithm (issueScopedToken: base64url(payload).hmac_sha256(secret)). While cryptographically sound using crypto.timingSafeEqual, tokens are completely stateless without token revocation or rotation. Volunteer tokens are configured with an 8-hour lifetime (VOLUNTEER_SESSION_TTL_SECONDS = 28800).

Exploit Scenario: If an event volunteer's device is compromised or a token is intercepted on an insecure network, an attacker can perform check-ins and extract rider data for up to 8 hours, even if the admin resets or deactivates the volunteer's account in the database.

Remediation: Validate that the volunteer account is still active on each authenticated request by querying the database in requireVolunteer, or store a token issue timestamp in volunteer_accounts and invalidate tokens issued prior to account updates.

3. In-Memory Rate Limiter in Multi-Process / Cluster Deployments

MEDIUM (CVSS 5.3)

File Affected: backend/src/middleware/rateLimit.js

Vulnerability Description: The rate limiter keeps hits in an in-memory Map. If the application is deployed behind a load balancer with multiple Node.js worker processes (e.g. PM2 cluster or Kubernetes pods), each process maintains its own memory table. An attacker can distribute requests across processes, effectively multiplying the allowed threshold.

Remediation: For distributed production deployments, swap the in-memory rate limiter with a Redis-backed token bucket (e.g. ioredis or rate-limiter-flexible).

4. Missing CSRF Defense on Same-Site Cookie Scenarios (Defense in Depth)

LOW (CVSS 3.1)

File Affected: backend/src/app.js

Vulnerability Description: While the application currently uses Authorization: Bearer <token> (which is immune to standard cross-site request forgery), if session handling is ever extended to cookies without anti-CSRF tokens, cross-origin mutations could occur.

Remediation: Continue using Authorization header tokens exclusively and do not transition to ambient session cookies without pairing with SameSite=Strict and CSRF double-submit cookies.

09 Performance, Operations & Deployment

The NV Cyclothon infrastructure is optimized for both cost efficiency and race-day high concurrency.

Production Deployment Architecture

  • Containerization: Docker and docker-compose configurations are ready for deployment on any standard VPS or cloud container service (e.g. AWS ECS, GCP Cloud Run, or DigitalOcean).
  • Database Optimization: Connection pooling is pre-tuned. cyclothon_registrations features compound indexes on (status, created_at DESC) and case-insensitive unique indexes on lower(email) for fast lookups.
  • Static Asset Delivery: Vite bundles are code-split into distinct chunks (e.g. VendorPage at 20 KB, PartnerPage at 51 KB). Re-usable assets are configured with long-term immutable caching headers.
  • Document Generation Caching: Generated Rider Passes and Participation Certificates are cached on disk as static PDFs using a content-hash key (rider-pass-2026-approved-v2-{id}.pdf). Repeated downloads do not incur PDF rendering overhead.
